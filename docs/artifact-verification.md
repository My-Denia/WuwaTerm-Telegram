# Core artifact verification

`core-lock.json` is the consumer-side trust root. It pins the published WuwaTerm Core `0.8.2` release: the wheel filename and SHA-256, the release tag, the source commit that tag peels to, and the asset URL. The Telegram `0.2.5` release is built against that wheel. The lock records the intended release; it does not replace that release's own provenance.

The version 2 lock has two producer kinds. `github-release` records the tag, source commit, wheel filename and digest, and the asset URL derived from the repository, tag and filename. `github-actions-artifact` records repository and workflow IDs, the run ID and attempt, event, run head, checkout commit and tree, artifact ID, name, archive digest, size and expiry, and the wheel and source distribution names and digests. GitHub's pull-request run head and the commit checked out by that run can differ. For an artifact the fetcher checks the run head against run and artifact records, and checks the checkout independently against the reusable packaging workflow reference and the Git commit API's tree. It then verifies the downloaded archive bytes, its source manifest, checksums and both distribution hashes. The downloaded manifest is not the trust root. That artifact has an expiry date, and a consumer repository's default token may not be allowed to download it across repositories.

For the release kind the fetcher checks the release record and that it is not a draft, requires exactly the recorded asset with the recorded download URL, resolves the tag to the recorded source commit, and verifies the pinned wheel digest and metadata. Release assets are public, so no cross-repository token permission is needed and nothing expires. There is no floating or `latest` fallback, and no future URL is inferred.

CI runs the fetch before pip with the consumer's own default token, which raises GitHub API rate limits. A 403 or other HTTP denial reports the status without printing response bodies or tokens. A successful local download with another credential is not evidence that CI will pass.

To change the pinned Core release, update the Core dependency in `pyproject.toml`, the runtime compatibility constant, the artifact lock and the verified installer/container inputs together. Re-run the download, clean wheel and sdist installs, runtime checks, and CI against the actual release artifact.
